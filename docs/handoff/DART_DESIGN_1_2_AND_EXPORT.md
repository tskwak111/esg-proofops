# 스키마 1.2와 보고서 노출 설계안

2026-10-09 · D-13 / D-15 · **설계만 작성. 실행 코드·스키마·내보내기 미변경.**

사용자 범위 결정: C1~C4 구현을 진행하되 스키마 1.2와 보고서 노출은
설계까지만 진행한다. 아래 필드명과 경로는 제안이며 현재 API가 수용하지 않는다.
정책값, 시설-법인 관계, 실기업 정답을 이 문서로 승인하지 않는다.

## D-13: 별도 버전으로 도입

현재 `contracts/reconciliation/{input,policy,output}.schema.json` 및 패키지 내
1.1 스키마를 바꾸지 않는다. 구현이 승인되면 `contracts/reconciliation/1.2/`
아래 별도 세 파일과 별도 버전 reader를 추가한다. 1.1 엔진과 정규화 로직을
버전별로 유지하고, 저장된 revision의 엔진 버전과 정책 해시로 재생한다.
1.1 reader에 1.2 입력을 보내면 명시적인 unsupported-version으로 거부한다.
구버전 reader가 새 필드를 묵시적으로 무시하거나 1.1로 해석하게 만들지 않는다.

### 시설-법인 매핑

입력 확장 후보 `facility_entity_mappings[]`:

| 필드 | 제약 |
| --- | --- |
| `facility_id`, `entity_id` | 각각 해당 입력의 명시적 식별자에 존재 |
| `relation` | 승인된 유한 목록; 소유·운영·보고포함을 서로 구분 |
| `valid_from`, `valid_to` | 근거가 명시하는 적용기간. 날짜 추정 금지 |
| `source_ids` | 매핑 자체를 뒷받침하는 원문 인용, 비어 있으면 거부 |
| `mapping_id` | revision 내부 고유 식별자 |

인용은 원문 해시·locator·quote로 검증하고, 인증된 검토자가 정확한 관계와
적용기간을 확인해야 한다. 공통 상호, 주소 유사도, 임베딩으로 매핑을 승인하지
않는다. 다대다 관계를 허용하되 누락 시설, 중복 산입, 충돌 관계와 기간 공백을
명시적으로 처리한다. 전체 검증된 매핑으로 재무 범위와 같은 집합이 만들어질
때만 matched 후보가 된다. 일부 매핑만 있는 경우 완전 일치로 올리지 않는다.

### 다년 CAPEX

입력 확장 후보 `capex_schedule[]`에 `period_start`, `period_end`, `amount`,
`currency`, `unit_scale`, `basis`(약정/계획/실행), `source_ids`를 둔다.
총액과 연도별 분해가 함께 있으면 동일 금액을 두 번 합산하지 않는다.
정책에는 비교 가능한 basis와 합산 허용 규칙을 별도로 버전 고정한다.
환율, 물가조정, 연율화, 기간 안분은 기본 비활성이고 임의 기본값을 두지 않는다.
기간 미상, 겹침, 통화 혼합, 기준 불일치, 근거 없는 자금조달 계획은 blocked로
유지한다. 1.1 단일기간 입력을 자동으로 다년 일정으로 확장하지 않는다.

### 저장·전환·롤백

1. 기존 1.1 revision과 정책/원문을 바이트 그대로 보존한다.
2. 신규 케이스만 명시적 버전 선택으로 1.2에 등록한다. 기존 케이스 변환은
   새 revision과 변환 근거를 만들며 이전 결과를 덮어쓰지 않는다.
3. 서버 지원 버전과 UI 지원 버전을 함께 확인하고, 등록 시 unsupported-version을
   먼저 거부한다. 평가 시 버전별 엔진/정책/입력 해시를 결속한다.
4. 롤백은 1.2 등록과 평가만 비활성화한다. 과거 1.2 기록은 삭제하지 않으며
   해당 reader가 없는 배포에서는 원본 보존 상태만 명시한다.

구현 전 승인할 사항: 매핑 관계 어휘, 다년 합산 정책, 비교 기준, 승인자,
엔진 버전 보존 방식. 구현 승인 후 필수 테스트: 1.1 골든 바이트 재생,
미지원 reader 거부, 다대다/중복/기간공백/통화혼합, 변환 감사 이력,
마이그레이션 실패 롤백 및 이전 revision 재생.

## D-15: 독립된 대사 부록

현재 `exports.py`와 `export_store.py`를 변경하지 않는다. 구현 승인 후
명시적인 `include_reconciliation` 옵션과 별도 기능 플래그를 제안한다.
기본값은 false이고 기존 내보내기 경로의 바이트와 G/P/M 등급·라벨은 유지한다.
ON이면 별도 부록 또는 별도 파일에 대사 결과를 표시하며 본 등급에 합산하지 않는다.

부록은 회사/사업연도/연결구분/평가기준일/고정 접수번호, 케이스와 revision,
입력·정책·엔진 해시, 검토·승인 상태, execution_state/status/reason,
원문 인용과 검색 범위, synthetic 표시를 포함한다. unknown/blocked/not_run과
분모 제외 사유를 숨기지 않고, 결과가 없으면 결과 없음으로 표시한다.

요청 시 현재 head를 조용히 읽는 대신 export manifest에 선택된 case revision을
고정한다. 다른 테넌트 원문은 접근할 수 없고, 원문 변조나 stale revision은
실패한다. PDF 부록의 텍스트는 escape하고 로컬 파일 경로·키·활성 HTML을 넣지
않는다. 대사 실패를 G/P/M 내보내기 성공처럼 포장하지 않는다.

구현 전 A/B 합의할 사항: 별도 파일 대 PDF 부록, export manifest 버전,
revision 선택 UI, 보존 정책. 구현 승인 후 테스트: OFF 기존 바이트 동일,
ON 별도 섹션, 합성 표시, 모든 차단 사유 표시, 교차테넌트 404,
원문 변조 거부, 동일 manifest의 결정적 재생, 동시 head 변경 시 CAS.
