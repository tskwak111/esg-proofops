## 기업 분리 평가

개발자 B의 명시된 개발 기업은 삼성전자, 이번에 처음 수집한 평가 기업은 오뚜기·동서다.
기존 프로젝트의 전체 기업 코퍼스가 독립 검증된 것은 아니므로 전역 holdout 성능이라고
표현하지 않는다. 기대값은 후보 출력 복사가 아니라 원본 재무제표 JSON의 모든 행을
계약에 맞춰 별도로 직렬화하여 작성했다.

최종 실행(`evaluation/real-benchmark-final.json`)에서 원문 9/9,
재무제표 기업·연도·접수번호 3/3, 후보 기업 연결 3/3,
행의 기대값·인용 위치 372/372가 일치했다.
이 중 새 기업은 362행, 삼성 개발 표본은 10행이다. 정답 태깅·회계 의미·등급 정확도가
아닌 원문 보존과 위치 재현 지표다. 전 기업 후보가 제한되어 `truncated=true`이므로
전체 케이스 판정은 `fail / candidate_catalog_truncated_incomplete_search`다.
이 경고를 없애거나 전체 검색 완료로 승격하지 않았다.

## 구현과 검증 연결

- `evaluation.reconciliation_source_audit`: 원문 재구성·인용 검사·미승인 계정 초안.
- `evaluation.reconciliation_benchmark`: 불변 평가 결과·기업 분리·원문/위치 검증.
- `scripts/check_reconciliation_readiness.py`: 로컬 실행 환경, 저장소, 복구·롤백 준비 검사.
- `scripts/verify_reconciliation.py`: 신규 도구를 기존 릴리스 lint/type/test 경로에 포함.

Node 24가 CI 기준과 달랐으므로 fnm에 Node 22.23.2를 추가 설치했다.
전역 기본 버전을 바꾸지 않고 `fnm exec --using 22`로 실행했다.
해당 Node 환경에서 web typecheck와 production build를 통과했다.

최종 평가·원문 도구 집중 검사 31개 통과, Linux 대상 mypy 207개 파일 통과.
최종 원문 재실행은 각 기술 보고서와 평가기 코드의 SHA-256을 함께 기록했다.
최종 준비 검사(`deployment/readiness-final/readiness.json`)는 로컬 27개 항목을
통과했다. 클라우드 4개 차단·2개 미실행은 이번 운영 배포 제외 범위를 그대로 표시한다.
공개 등록·검토 메서드를 사용하는 저장소 복구 회귀에서는 합성 parser/model/reviewer
입력으로 실제 DB·파일을 등록하고 revision 2까지 저장한 뒤 복원했다.
복원본의 claim·case·revision·원문과 멱등 재요청이 일치했으며 원래 파일로의
우회 읽기와 복원 원문 변조를 거부했다. 이는 실제 기업 승인이나 모델 실행 증거가 아니다.
복구 문서는 원문·`parser-prepared`·대조 파일과 DB를 함께 백업하도록 정리했다.
