# 연계 검증 모듈 명세 (Reconciliation Module)

대상: 지속가능성 공시 입증 검토 시스템 v2.2
작성일: 2026-09-14
선행 문서: 프로젝트 문서 v2.2 (4.5절 C군, 4.10절 출력 규칙), 기준반영 개선요청서 3.8절

---

## 1. 이 모듈이 하는 일

지속가능경영보고서(또는 사업보고서 지속가능성 정보란)의 클레임을, **같은 기업이 같은 기간에 공시한 재무제표·주석**과 대조한다.

### 1.1 판정 대상을 정확히 이해할 것 — 이 절을 건너뛰지 말 것

```
❌ 판정하지 않는 것:  "두 값이 같은가"
✅ 판정하는 것:      "두 값이 다르다면, 그 차이를 설명하는 문구가 공시에 있는가"
```

재무제표는 K-IFRS 연결(지배력) 기준을, 온실가스 배출량은 GHG Protocol 운영통제 기준을 쓴다. **값이 달라야 맞는 경우가 대다수다.** 값 불일치를 곧바로 문제로 띄우면 오탐이 쏟아지고 제품이 버려진다.

근거는 IFRS S1 문단 21이다. 기업은 지속가능성 관련 재무공시와 재무제표를 포함한 다른 일반목적재무보고서 간의 **연계를 이용자가 이해할 수 있도록** 정보를 제공해야 한다(세부 문단 B39~B44). 요구되는 것은 값의 동일성이 아니라 **연계의 설명 가능성**이다.

### 1.2 범위 밖

- 회계 처리의 적정성 판단 (충당부채 과소계상 여부 등) — **절대 하지 않는다**
- 뉴스·NGO 보도·제3자 배출량 DB 등 외부 데이터 대조 — 별개 기능이며 이 모듈에 포함하지 않는다
- 재무제표 자체의 오류 탐지

### 1.3 회계 판단 금지 — 경계선 (반드시 읽을 것)

**전제: 우리 팀에는 회계 도메인 전문가가 없다.** 이 사실이 이 모듈의 설계 제약이며, 아래 경계선은 "조심하자"는 권고가 아니라 **구현 금지 사항**이다.

문제는 개발자가 회계 전공이 아니면 **자기가 선을 넘는 줄 모른다**는 점이다. 그래서 무엇이 회계 판단인지를 구체적으로 적는다.

#### 해도 되는 것 — 존재 확인과 값 비교

| 유형 | 예 |
|---|---|
| 두 문서의 값이 같은지 비교 | 조직경계 5개 사업장 vs 종속기업 12개사 |
| 특정 항목이 문서에 **존재하는지** 확인 | 자본적지출 약정 주석에 해당 투자 계획이 기재되어 있는가 |
| 차이를 **설명하는 문구**가 있는지 탐색 | "운영통제 기준을 적용하여 지분법 대상은 제외하였습니다" |
| 분류 **기준이 공시되었는지** 확인 | 친환경 제품의 정의와 산정 기준이 제시되어 있는가 |
| 기간·단위·범위 표기 확인 | 보고기간이 결산일과 일치하는가 |

공통점: **문서에 쓰여 있는지 없는지만 본다.**

#### 절대 하면 안 되는 것 — 회계적 타당성 평가

| 유형 | 금지되는 산출 예시 |
|---|---|
| 인식 여부의 적정성 | "전환 리스크가 중대한데 손상차손이 인식되지 않았다" |
| 금액의 적정성 | "충당부채가 과소계상된 것으로 보인다" |
| 분류의 적정성 | "이 지출은 자본화가 아니라 비용 처리해야 한다" |
| 연결범위의 적정성 | "이 종속기업은 연결 대상에서 제외하면 안 된다" |
| 추정·가정의 합리성 | "내용연수 가정이 기후 리스크를 반영하지 못했다" |
| 재무 영향의 추정 | "이 리스크는 약 O억원의 손실로 이어질 것" |

**판별 질문**: 산출물에 "~해야 한다", "~가 누락되었다", "~이 적절하지 않다"가 들어가면 회계 판단이다. 우리 산출물은 **"~에 대한 설명이 확인되지 않았다"**까지만이다.

#### 구현상의 안전장치

1. **C5를 코드에서 하드 게이트로 막는다.** 설정에 `stage: 2`가 붙은 항목은 실행 자체가 차단되도록 구현한다. 주석 처리가 아니라 런타임 가드다.

```python
if rule.stage > CURRENT_STAGE:
    raise NotImplementedError(f"{rule.id} requires accounting domain review")
```

2. **금지 어휘 필터.** 산출 문구 생성 시 아래 어휘가 포함되면 차단하고 검토 큐로 보낸다.
   `과소계상, 과대계상, 누락되었, 인식하여야, 계상하여야, 부적절, 위반, 오류, 손상차손을, 자본화해야`

3. **C3 임계값은 판단이 아니라 규칙이다.** 임계값을 넘었다는 것은 "설명이 필요하다"는 뜻이지 "투자 계획이 허위다"가 아니다. 임계값은 설정 파일에 외부화하고 코드에 하드코딩하지 않는다.

4. **테스트 케이스로 고정한다.** 연계 정답셋(7.2절)에 "회계적으로는 문제가 있어 보이지만 우리는 판정하지 않아야 하는" 케이스를 최소 10건 포함하고, 시스템이 `not_applicable`을 반환하는지 회귀 검증한다.

#### 이것이 제약이 아니라 제품 정의인 이유

회계 판단은 감사인의 업무이고 면허가 필요하다. 우리가 그 영역에 발을 들이면 고객(회계법인·인증기관)의 업무를 침범하는 동시에 독립성 요건과 충돌한다. **경계선을 지키는 것이 그들에게 팔 수 있는 조건이다.**

## 2. 입력

### 2.1 지속가능성 측

기존 파이프라인 산출물을 그대로 사용한다.

```
claim_id, quote, statement, track, topic, page,
elements[]        // 태깅된 입증요소와 evidence_span
dart_corp_code, fiscal_year, reporting_period
```

### 2.2 재무 측 — DART Open API 조회

**PDF 파싱이 아니라 항목 코드 조회다.** 별도 수집 경로로 구현할 것.

| 필요 데이터 | 용도 |
|---|---|
| 종속기업 목록 (주석) | C1 |
| 보고기간·결산일 | C2 |
| 현금흐름표 투자활동 | C3 |
| 자본적지출 약정 (주석) | C3 |
| 부문별 정보 (주석) | C4 |
| 연결/별도 구분 | 전 항목 |

**⚠ 착수 전 확인**: DART Open API가 종속기업 목록·부문별 정보·자본적지출 약정 주석을 구조화 형태로 제공하는지 실제 호출로 검증할 것. 제공되지 않는 항목은 사업보고서 본문 파싱으로 대체해야 하며, 그 경우 난이도가 달라진다.

### 2.3 대조 기간 결정 규칙

#### 원칙: 발간월이 아니라 보고대상기간에 건다

두 문서는 **발간월이 다를 뿐 보고대상기간은 같다.**

| 문서 | 발간 | 보고대상 |
|---|---|---|
| 사업보고서·재무제표 | 2025년 3월 | FY2024 |
| 지속가능경영보고서 | 2025년 6~7월 | FY2024 |

따라서 **동일 회계연도로 대조한다.** 발간 연도로 맞추면(FY2024 재무제표 ↔ FY2025 지속가능성 데이터) 연도가 어긋나 대조가 성립하지 않는다.

발간 순서는 오히려 검증의 정당성을 강화한다. 사업보고서가 먼저 확정되므로, 지속가능경영보고서 작성 시점에 기업은 **이미 확정된 재무 데이터를 보유하고 있다.** 두 문서가 어긋날 때 "몰랐다"는 항변이 성립하지 않는다.

#### 결정 순서

```
1. 지속가능경영보고서에서 보고대상기간을 추출  ← 발간월을 쓰지 않는다
       (표지, 보고서 개요, "보고 기간" 항목)
       추출 실패 시 → 사람 검토 큐. 추정하지 않는다

2. 해당 기간의 재무제표를 조회 (연결 기준)

3. 가용성 확인
   IF 재무제표 발간일 > 지속가능경영보고서 발간일:
       status = not_applicable
       reason = "financial_statement_published_later"
       # 드물지만 SR을 2~3월에 먼저 내는 기업이 있다

4. source_ref에 기록: fy, rcept_no(접수번호), 연결/별도, fetched_at
```

#### 반드시 처리할 예외

| 상황 | 처리 |
|---|---|
| **다년도 추이 표** — SR 데이터 섹션이 3개년을 함께 제시 | 문장이 **특정 연도를 명시한 경우에만** 대조. 미명시 시 `not_applicable` |
| **보고기간 종료 후 활동** — "2025년 상반기에는 ~" 서술이 FY2024 보고서에 포함 | `not_applicable`, reason = `period_out_of_scope` |
| **연결/별도 불일치** | 반드시 **연결 대 연결**. 별도와 대조하면 전부 불일치로 뜬다 |
| **정정공시** | 사업연도만으로 부족. **접수번호(rcept_no)까지 기록** |
| **통합보고서** (재무+지속가능성 합본) | 동일 문서이므로 외부 조회 불필요. 문서 내 대조로 처리 |
| **비12월 결산** | 보고대상기간을 결산월 기준으로 맞춘다 |

> 2028년부터 지속가능성 정보가 사업보고서에 함께 실리면 이 절 전체가 불필요해진다. 그때까지만 필요한 규칙이다.

## 3. 대조 항목 (C1~C5)

### C1 — 연결범위 일치 【1단계】

**발동 조건**: 클레임이 조직경계·사업장 범위를 언급 (태깅 요소 `organizational_boundary` 또는 `implementation_scope` present)

**대조**
```
지속가능성 측: 배출량 산정 조직경계 (예: "국내 5개 사업장", "전 사업장", "연결 기준")
재무 측:       종속기업 목록 주석의 연결 대상 기업 수·범위
```

**판정 로직**
```
IF 지속가능성 조직경계 == "연결 기준" AND 종속기업 수 일치:
    status = matched
ELIF 조직경계 기준이 명시되어 있고(지분율/재무통제/운영통제), 
     그 기준으로 인한 차이임이 설명되어 있음:
    status = matched
    explanation_present = true
ELIF 범위가 다르지만 설명 문구 없음:
    status = needs_explanation
ELSE:
    status = not_applicable
```

**허용 차이 유형** (`reconciliation_rules.yaml`에 등록 — 이 목록에 해당하면 오탐 방지 로직 작동)
- 운영통제 기준 vs 지배력 기준
- 해외 자회사 제외 (제외 사유가 기술된 경우)
- 지분법 적용 대상 제외
- 신규 취득·처분 기업의 기간 안분

### C2 — 보고기간 일치 【1단계】

**발동 조건**: 정량 성과 주장 (`quantitative_value` present)

**대조**: 지속가능성 정보의 기준일 ↔ 재무제표 결산일

**판정**: 불일치 시 `needs_explanation`. 단 데이터 수집 시차를 명시한 경우 `matched`.

### C3 — 정량 약속의 재무 근거 【1단계】

**발동 조건**: 금액을 명시한 투자·지출 약속 (목표형 트랙 + 통화 단위 숫자 포함)

**대조**
```
지속가능성 측: "2030년까지 친환경 설비에 3조원 투자"
재무 측:       현금흐름표 투자활동 추이, 자본적지출 약정 주석
```

**판정 로직**
```
IF 약정 주석에 해당 투자 계획이 기재됨:
    status = matched
ELIF 약속 금액이 현재 연간 CAPEX 규모 대비 현저히 크고(임계값: config)
     그 조달·집행 계획에 대한 설명이 없음:
    status = needs_explanation
ELSE:
    status = not_applicable   # 판단 근거 불충분
```

**⚠ 주의**: 미래 투자 약속은 회계상 약정으로 인식되지 않는 것이 정상이다. **약정 주석에 없다는 것만으로 문제로 띄우지 말 것.** `needs_explanation`은 규모가 비정상적으로 크고 설명이 전무할 때만.

### C4 — 분류 기준 공시 【1단계】

**발동 조건**: 매출·비중을 주장하는 클레임 (예: "친환경 제품 매출 비중 32%")

**대조**: 부문별 정보의 매출 구성

**판정**: 주장된 분류의 **정의와 산정 기준이 공시되어 있는지**가 핵심. 숫자 일치보다 분류 기준의 명시 여부를 본다. 기준이 없으면 `needs_explanation`.

### C5 — 재무영향 서술 정합 【2단계 — 1단계에 넣지 말 것】

**발동 조건**: 기후 관련 재무영향을 언급하는 클레임

**대조**: 전환 리스크 중대성 서술 ↔ 자산손상(K-IFRS 1036)·충당부채(1037) 주석

**미루는 이유**: 회계 판단이 개입하므로 도메인 지식 없이는 오탐이 쏟아진다. 손상 미인식이 정상인 경우가 대부분이며, 이를 문제로 띄우면 회계 판단으로 오인된다.

**구현 금지**: 설정의 `stage: 2` 항목은 런타임 가드로 차단한다(1.3절). 주석 처리가 아니라 예외 발생이다. 회계 전문가 검토를 거쳐 `CURRENT_STAGE`를 올리기 전까지 실행될 수 없어야 한다.

## 4. 출력 스키마

판정 결과의 **위치가 중요하다.** `label`과 `evidence_grade`에 절대 반영하지 않는다. 기존 등급 체계와 논문 재현성이 흔들린다.

```json
{
  "claim_id": "C-0042",
  "label": "INCOMPLETE",
  "evidence_grade": "E1",

  "reconciliation": [
    {
      "item": "organizational_boundary",
      "status": "needs_explanation",
      "sustainability_value": "국내 5개 사업장 기준",
      "financial_value": "종속기업 12개사 연결",
      "difference_note": "운영통제 기준 vs 지배력 기준",
      "allowed_difference_type": "operational_control_vs_control",
      "explanation_present": false,
      "explanation_location": null,
      "source_ref": {
        "system": "DART",
        "corp_code": "00126380",
        "fy": 2025,
        "item": "종속기업 목록 주석",
        "fetched_at": "2026-09-14T10:22:31Z"
      },
      "basis": [
        {"standard": "IFRS S1", "clause": "21", "text": "재무제표와의 연계 정보 제공"}
      ],
      "confidence": 0.86
    }
  ]
}
```

### 4.1 status 값은 세 개뿐

| 값 | 의미 |
|---|---|
| `matched` | 일치하거나, 차이가 있으나 설명이 공시에 존재 |
| `needs_explanation` | 차이가 있고 설명이 확인되지 않음 |
| `not_applicable` | 대조 대상 없음, 판단 근거 불충분, 재무제표 미공시 |

**`mismatch` · `error` · `violation` 같은 값을 만들지 말 것.** 값 이름 하나가 제품의 성격을 규정한다. 개발 중 편의상 추가하고 싶어지는 순간이 오는데, 그 값이 UI에 노출되면 회계 판단으로 오인된다.

### 4.2 UI 표기 문구

- `needs_explanation` → "설명 보완 권장" (❌ "불일치", "오류")
- 화면 하단 고정: *본 기능은 회계 처리의 적정성을 판단하지 않으며, 공시 간 차이에 대한 설명의 존재 여부만 점검합니다.*

## 5. 처리 흐름

```
[1] 클레임 로드
     ↓
[2] C군 발동 조건 평가 (코드)
     발동 항목 없음 → 종료
     ↓
[3] DART 조회 (경로 B)
     해당 사업연도 재무제표 없음 → not_applicable
     ↓
[4] 값 대조 (코드)                    ← LLM 사용 금지
     숫자 비교, 범위 비교, 단위 정규화
     ↓
[5] 허용 차이 유형 매칭 (코드)
     reconciliation_rules.yaml 조회
     ↓
[6] 차이 설명 문구 탐색 (RAG)          ← 여기서만 LLM
     보고서 전역 + 부록 + 주석에서 해당 차이를 설명하는 문구 검색
     찾으면 explanation_location 기록, 못 찾으면 반드시 null 반환
     ↓
[7] status 결정 (코드)
     ↓
[8] 저신뢰 건 → 검토 큐
```

**[4]와 [7]은 코드가 한다.** LLM은 [6]에서만 쓰이며, 하는 일은 문서에서 설명 문구를 찾는 것뿐이다. 판정은 하지 않는다. 기존 시스템의 "LLM은 독해, 판정은 규칙엔진" 원칙이 이 모듈에도 그대로 적용된다.

**[6]의 환각 차단**: 설명 문구를 찾지 못하면 반드시 `null`을 반환하도록 강제한다. 찾았다고 주장하면 `explanation_location`의 실재 여부를 코드로 검증하고, 실재하지 않으면 무효 처리 후 검토 큐로 보낸다.

## 7. 평가

### 7.1 지표 — 정밀도가 주 지표다

연계 판정은 재현율보다 **정밀도가 결정적으로 중요하다.** 놓치는 것은 아쉬운 수준이지만, 정상적인 차이를 문제로 띄우면 기업 고객은 한 번에 도구를 버린다.

| 지표 | 목표 | 우선순위 |
|---|---|---|
| 연계 판정 정밀도 | — | **주 지표** |
| **정상 차이 오탐률** | **5% 미만** | **주 지표** |
| 연계 판정 재현율 | — | 보조 |
| DART 조회 성공률 | 98% 이상 | 운영 |

### 7.2 연계 전용 정답셋

**기존 골드셋으로는 이 모듈을 평가할 수 없다.** 문장 내부 요소만 정답으로 갖고 있기 때문이다. 별도 정답셋을 구축한다.

- 규모: 항목별 30건, C1~C4 합계 약 120건
- **구성을 네 유형으로 균등 배분할 것**

| 유형 | 정답 | 검증 목적 |
|---|---|---|
| 일치 | `matched` | 기본 동작 |
| 설명 있는 차이 | `matched` | 설명 탐색(RAG) 정확도 |
| 설명 없는 차이 | `needs_explanation` | 탐지 능력 |
| **정상 차이** | `matched` 또는 `not_applicable` | **오탐 방지 — 가장 중요** |
| **회계 판단 유혹 케이스** | `not_applicable` | **경계선 준수 검증 (최소 10건)** |

마지막 유형은 "회계적으로는 문제가 있어 보이지만 우리는 판정하지 않아야 하는" 사례다(예: 전환 리스크를 중대하다고 서술했으나 손상차손 인식이 없는 경우). 시스템이 `not_applicable`을 반환하는지 회귀 검증한다. **여기서 `needs_explanation`이 나오면 경계선을 넘은 것이다.**

"정상 차이" 유형이 이 정답셋의 핵심이다. 연결범위와 조직경계가 다른 것이 정상인 사례를 시스템이 조용히 넘기는지가 제품 성패를 가른다.

## 9. 개발 중 반드시 지킬 다섯 가지

1. **`status`에 네 번째 값을 만들지 않는다.** 개발 편의상 `mismatch`를 추가하고 싶어지는 순간이 오는데, 그 값이 UI에 닿으면 제품이 회계 판단 도구로 오인된다.

2. **`label`과 `evidence_grade`를 건드리지 않는다.** 연계 결과는 별도 축이다. 기존 등급 체계에 섞으면 논문 재현성과 기존 골드셋이 전부 무효가 된다.

3. **설명 문구를 못 찾으면 `null`을 반환한다.** [6]단계에서 LLM이 "설명이 있는 것 같다"고 추정하는 순간 이 모듈의 신뢰도가 사라진다. 반환된 위치는 코드로 실재 검증한다.

4. **회계 판단 경계선을 넘지 않는다(1.3절).** 산출 문구가 "~해야 한다 / ~가 누락되었다 / ~이 부적절하다"로 끝나면 선을 넘은 것이다. 우리 산출물은 **"~에 대한 설명이 확인되지 않았다"**까지다. C5는 런타임 가드로 차단하고, 금지 어휘 필터를 통과하지 못한 문구는 검토 큐로 보낸다.

5. **대조 기간은 보고대상기간으로 결정한다(2.3절).** 발간월을 기준으로 삼으면 예외 처리가 끝없이 늘어난다. 보고대상기간 추출에 실패하면 추정하지 말고 검토 큐로 보낸다.
