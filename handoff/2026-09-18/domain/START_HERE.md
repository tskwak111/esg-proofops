# 도메인·데이터 담당자에게

코딩은 하지 않아도 됩니다. CSV는 Excel/Numbers로 열어 작성할 수 있습니다.
당신의 가장 중요한 일은 모델이 맞는지를 판별할 원문 정답과, 애매한 규칙의 경계 사례를 만드는 것입니다.
회계·법률 전문가 자격을 전제로 맡기는 업무가 아닙니다. 판단할 수 없으면 unresolved로 제출합니다.

## 제출 파일
| 파일 | 작성 단위 | 할 일 |
|---|---|---|
| corpus.csv | 문서 1행 | 기업·보고기간·원문 URL·버전·권리·개발/평가 분리 |
| claims.csv | 원자 주장 1행 | 문장 원문과 물리 페이지, 주장 분리, 트랙 |
| elements.csv | 주장×요소 1행 | present/absent/unknown/conflict/not_applicable와 원문 위치 |
| numeric.csv | 값·연도·단위 조합 1행 | 표/셀/각주 조건과 비교 정답 |
| assurance.csv | 주장×보증서 1행 | 기간·경계·지표·제외와 covered 판단 |
| reconciliation.csv | 주장×C항목 1행 | 양쪽 공시 원문, 비교 가능성, 차이 설명의 존재 |
| rules.csv | 규칙 질문 1행 | 이미 채운 18개 질문에 제안·근거·양성/음성/경계 사례 |
| acceptance.csv | 성능 지표 1행 | 합격선 제안·분모·범위·관측값·검토 상태 |

행의 빈칸을 임의 값으로 채우지 마세요. 모르는 것은 unknown/unresolved, 없는 위치는 빈칸으로 남기고 사유를 씁니다.
헤더는 바꾸지 말고 복사본에 작업합니다. 예: submissions/2026-09-25/reviewer-name/.

## 우선순위와 첫 제출 (착수 후 3근무일을 제안)
1. 서로 다른 기업 3곳의 문서 목록과 FY/원문 위치를 확인합니다.
2. 목표·성과·관리 주장을 합계 15개 이상 선정하고 요소 30개 이상을 직접 태깅합니다.
3. 잘못 붙이기 쉬운 표/각주 10개, 보증 범위 제외 사례 5개를 준비합니다.
4. GAP-003/004/007 및 REC-001/003/004/005 질문부터 사례와 의견을 제출합니다.
5. A와 45분 pilot 검토 후 태깅 지침을 수정하고 본 작업을 시작합니다.
위 수량은 새 협업 pilot 제안이며 현재 보유한 정답 수가 아닙니다.

## 본 평가용 데이터 목표 (기존 기준 + 신규 계획)
기존 계획: 최소 100 gold claims, 200 요소, 100 수치 tuple, 보증 음성 50건.
연계 문서 목표: C1~C4 항목별 30건, 총 약 120건. 우선 C1 30건 → C3 30건.
각 항목 30건은 일치/설명 있는 차이/설명 없는 차이/정상 차이를 7~8건씩 배분합니다.
회계 판단 유혹 사례 최소 10건은 별도 challenge 묶음으로 두고 중복 집계 여부를 표시합니다.
자료 확보가 안 되면 합성 예제로 대체해 gold라고 부르지 않습니다.

## 규칙 결정의 책임
- 당신: 원문 확인·태그 초안·해석 제안·공식 출처와 사례 정리.
- A: 구현 영향·기존 규칙과의 일관성 확인, 사용자/제품 책임자의 승인 기록 관리.
- 전문 검토가 필요한 회계·법적 기준: 별도 적격 검토자가 확인할 때까지 미정 유지.
- 문서의 조항 번호·효력·라이선스는 검증 전 사실 확정하지 않습니다.
- 결과 라벨을 원하는 대로 고르는 대신 요소를 태깅합니다. 최종 라벨 gold는 승인 규칙으로 유도하고 분쟁은 별도로 기록합니다.

## 독립성
기업 단위로 train/dev/test를 고정합니다. 같은 기업의 다른 연도도 같은 split에 둡니다.
이미 개발에 사용한 POSCO·Samsung Life·Kia·Kakao·KB·Naver 등의 실제 사용 이력을 A에게 확인하고 새 holdout으로 재사용하지 않습니다.
모델 예측을 보기 전에 주석합니다. 모델 초안은 silver이며 사람이 원문 검토해 승인한 기록과 구분합니다.
도메인 담당 1명의 검토만으로 전문가 간 일치도를 주장하지 않습니다. A가 일부를 독립 검토하더라도 회계 전문 검증을 대신하지 않습니다.
